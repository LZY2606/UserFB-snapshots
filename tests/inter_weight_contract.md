# inter_weight_contract — 帧间预测数值契约回归

`tests/inter_weight_contract.cc` 是一套针对 libde265 帧间预测（分数样本插值 +
加权预测）的数值回归。它不依赖任何外部码流：每个用例手工搭建真实的
`seq_parameter_set`、`pic_parameter_set`、`slice_segment_header`、`de265_image`
和 `PBMotion`，直接调用生产入口 `generate_inter_prediction_samples()`，再把三个
输出平面的**每一个样本**与一个独立坐标模型逐项比对（精确相等，无容差）。

## 结构

- **参考图像获取路径与真实解码一致**：slice 头的 `RefPicList[list][refIdx]` 给出
  帧编号，一个小的 `base_context` 子类（`RefContext`）把帧编号解析成固定的
  `de265_image`。期望的预测数组从不进入生产路径。
- **参考纹理**：确定性哈希纹理（一半样本被推到取值范围两端），非平坦；两个参考
  帧（id 1、2）纹理不同，用例里显式断言两者可区分；同一帧同时出现在两个列表的
  情形由 `same_ref_same_mv_distinct_weights` 覆盖。
- **独立模型**：用明确写出的 HEVC 亮度八抽头（相位 1/3 用 7 抽头）、色度四抽头
  系数表逐坐标计算，不调用任何生产插值/加权函数，也不缓存原版输出。有符号数
  除以 2 的幂一律定义为向下取整（`floor_shr`）。水平滤波之后、垂直滤波之前的
  中间值保持规定精度（`>>shift1` 截断），**不提前裁剪到像素范围**；坐标按真实
  平面尺寸逐点夹取，不依赖库的 padding。
- **校验内容**：块内每个样本等于模型值；块外和行尾（stride 大于图像宽度的
  padding 区）保持调用前写入的哨兵值；参考图像逐样本与调用前快照一致；
  解码上下文没有产生任何 warning；`integrity` 保持 `INTEGRITY_CORRECT`。
  此外每个用例用 `TASK_CHECK` 断言它声称覆盖的情形确实发生（负中间值、不能
  整除的水平中间值、边缘复制、整像素内部直取、末级饱和）。
- **高位深 stride**：`get_image_stride()` 返回的是样本数而不是字节数；12 位
  用例（`planes/highbd_stride_units`）直接断言样本坐标 (x,y) 的字节地址等于
  `plane + (y*stride+x)*2`，防止样本 stride 与字节 stride 混用。

## 用例

precision 组（内部精度）：

| 用例 | 内容 |
|---|---|
| `luma_hpass_truncation_10bit` | 10 位，亮度水平相位 1、垂直相位 0；水平中间值截断（含手算样例 1） |
| `luma_bidir_negative_mv_12bit` | 12 位，负运动向量，亮度相位 (2,3)、色度相位 (6,3)，左上角边缘复制 |
| `chroma_eighthpel_8bit` | 8 位，亮度相位 (3,1)、色度八分之一相位 (3,5) 双方向 |

lists 组（列表与权重接线）：

| 用例 | 内容 |
|---|---|
| `p_single_unweighted_fullpel_8bit` | 单列表普通，整像素，块完全在参考内部（直接取样路径） |
| `p_single_explicit_weight_10bit` | 单列表显式加权：负亮度权重、正负 offset、亮度/两路色度参数各异 |
| `b_bi_average_8bit` | 双列表普通平均，两个可区分的参考，运动向量一正一负，右边缘复制 |
| `b_bi_explicit_weight_12bit` | 双列表显式加权，L0 经 refIdx=1 间接取参考，每列表每分量权重不同 |
| `same_ref_same_mv_distinct_weights` | 同一参考身份（L0[0] 与 L1[1] 同为帧 1）、相同向量、两列表权重不同（含手算样例 2） |

planes 组（平面、stride、哨兵）：

| 用例 | 内容 |
|---|---|
| `ycbcr_420_8bit_all_planes` | 8 位双列表平均，三个平面都有双方向分数运动，块不在原点 |
| `edge_clipping_negative_mv_10bit` | 10 位，强负运动向量，亮度/色度垂直单方向滤波，全平面边缘复制 |
| `saturation_12bit_weighted` | 12 位显式加权，权重/offset 把末级分别压到 0 和 4095 饱和 |
| `highbd_stride_units` | 12 位样本 stride 与字节 stride 的单位关系 |

四种接法——单列表普通、单列表显式加权、双列表普通平均、双列表显式加权——
分别由 lists 组的前四个/五个用例覆盖。8、10、12 位 4:2:0，整像素、水平单方向、
垂直单方向、双方向，正、负运动向量，边缘复制与内部直取，在套件中均至少出现
一次并被相应的覆盖断言锁定。

## 手算样例 1：中间截断 ≠ 加半舍入

用例 `precision/luma_hpass_truncation_10bit`：10 位，P slice，单列表无权重，
MV=(1,0)（xFrac=1，yFrac=0），块位于 (8,8)，xInt=8、yInt=8。

块内像素 (0,1)（即输出样本 (8,9)）的 7 个水平抽头取自参考帧 1 第 9 行第
5..11 列：

```
p = (587, 1023, 0, 257, 1023, 1023, 1023)
S = -1*587 + 4*1023 - 10*0 + 58*257 + 17*1023 - 5*1023 + 1*1023 = 31710
```

shift1 = min(4, 10-8) = 2：

- 规定的截断：t = ⌊31710 / 4⌋ = **7927**
- 加半舍入（退化）：t' = ⌊(31710 + 2) / 4⌋ = **7928**

yFrac=0，垂直方向直通；末级（单列表无权重）shift = max(2, 14-10) = 4、
offset = 8：

- 正确：⌊(7927 + 8) / 16⌋ = ⌊7935/16⌋ = **495**
- 退化：⌊(7928 + 8) / 16⌋ = **496**

测试把 (8,9) 锚定为字面量 495。

同一块内像素 (2,7)（输出 (10,15)）演示负中间值：抽头为第 15 行第 7..13 列
`(0, 385, 1023, 0, 0, 816, 0)`，S = 4*385 − 10*1023 − 5*816 = **−12770**，
中间值 t = ⌊−12770/4⌋ = **−3193**（保留，不裁剪）；末级 ⌊(−3193+8)/16⌋ =
−200，最终饱和裁剪到 **0**（第二个锚点）。

## 手算样例 2：合并 ≠ 独立加权

用例 `lists/same_ref_same_mv_distinct_weights`：8 位，B slice，显式加权双预测；
`RefPicList[0][0] = RefPicList[1][1] = 帧 1`（同一参考身份），两个列表的 MV 都是
(4,0)（整像素），块位于 (16,8)。锚定像素 (0,0)（输出 (16,8)）取自参考 (17,8)，
样本值 R = 124，中间值 in = 124 << 6 = 7936。

denom = 0 → log2WD = 6；L0：w0=1、o0=1；L1：w1=2、o1=−2（8 位 offsetShift=0，
offset 不放大）：

- 正确的双列表独立加权：rnd = (o0+o1+1)·2^6 = (1−2+1)·64 = 0，
  out = ⌊(7936·1 + 7936·2 + 0) / 2^7⌋ = ⌊23808/128⌋ = **186**
- 退化（显式加权下仍合并相同参考+向量，退化成 L0 单列表加权）：
  out = ⌊(7936·1 + 32) / 2^6⌋ + 1 = 124 + 1 = **125**
- 若按普通平均合并：⌊(7936+7936+64) / 2^7⌋ = **124**

三者互不相同，测试把 (16,8) 锚定为字面量 186。

## 退化实验记录

两种可编译的退化分别注入、重新编译库并运行本套件（之后均已还原）：

1. **显式加权下仍合并**：`motion.cc` 的 `generate_inter_prediction_samples`
   中把 `if (!weightedPredFlag)` 改为 `if (true)`。
   第一个差异：`lists` 组 `same_ref_same_mv_distinct_weights`，亮度平面
   (16,8)：期望 186，实得 125（共 48 处不匹配）——正是手算样例 2 的两个数。
2. **水平滤波加半舍入**：`fallback-motion.cc` 的 `put_qpel_fallback` 三个非零
   亮度水平相位分支，把 `>>shift1` 改为 `(… + ((1<<shift1)>>1)) >> shift1`。
   第一个差异：`precision` 组 `luma_hpass_truncation_10bit`，亮度平面 (8,9)：
   期望 495，实得 496（共 3 处不匹配）——正是手算样例 1 的两个数。

两种退化由不同组、不同用例、不同样本值检出；正常源码精确通过全部 12 个用例。

## 旧测试为什么覆盖不到

- `task_support/baseline.cpp` 只对随源码的 8 位码流 girlshy.h265 的解码结果做
  整体哈希。退化 2 只影响 BitDepth>8 的水平中间截断（8 位时 shift1=0，加不加
  半个单位结果完全相同），任何 8 位码流在原理上就无法暴露它；该流也不含
  10/12 位内容、不含本套件构造的显式加权场景。
- 退化 1 只在"显式加权 + 双列表 + 同参考身份 + 同向量"同时成立时出错；普通
  编码流极少使用显式加权预测，这种构造条件更不会自然出现。即使哈希变化，
  解码摘要也只能说"输出变了"，无法定位到权重选择逻辑，也证明不了负瓣滤波
  的中间精度被保留。
- `task_support/upstream/test-cabac.cc` 只测 CABAC 编解码，不经过运动补偿。

## 运行

```
bash task_support/run.sh target
```

编译本文件，逐组核实断言确实执行（driver 要求每组至少一个用例、每个用例至少
一次 TASK_CHECK），随后联跑现有的公开解码对照（baseline 与 upstream cabac）。
