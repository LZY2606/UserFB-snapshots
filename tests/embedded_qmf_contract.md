# embedded_qmf_contract 回归测试：参照来源说明

`tests/embedded_qmf_contract.c` 是一套纯 C 回归（只依赖系统数学库，运行期间不下载
语音），目的是把"码流对不对"和"声音对不对"区分开，为后续调整打包和滤波实现兜底。
本文档说明每个参照从哪来、各自负责什么，以及旧测试覆盖不到的地方。

## 旧测试覆盖不到的地方

- `tests/test_encode_decode.py` 等 Python 测试把同一段输入在 3 种码率 × 2 种采样率
  下的码流和解码 PCM 用 MD5 固定。它能发现"行为变了"，但说明不了 64/56/48 kbps
  三种嵌入式码率之间的状态关系（同一个低带自适应是否在三种解码器里锁定），也把
  码流错和声音错混在一起，定位不了是 ADPCM 还是 QMF 滤波的问题，尤其定位不了
  滤波的相位/方向偏差。
- `checks/baseline.c` 做往返和分块一致性。若编码端和解码端的滤波同时写错（例如
  系数方向同时反），往返仍然自洽；这类"同谋错误"没有任何参照能发现。
- packed（48/56 kbps 位流）路径在旧测试里完全没有覆盖。

## 参照从哪来

### 共用数据

- QMF 系数、量化表 qm2/qm4/qm5/qm6、自适应初值（低带 `det=32`、高带 `det=8`）
  来自 ITU-T G.722 规范表格，测试文件内以 `ref_*` 常量独立保存。
- ADPCM 部分的参照是库自身的 ITU test mode（`itu_test_mode=1`，经公开结构体
  字段开启）。ITU 模式跳过 QMF，只提供 ADPCM 那一部分（低带索引、高带索引、
  真实重建的子带），**不能**提供滤波的期望值——滤波的期望值全部来自测试自己
  写的卷积。

### embedded 组（嵌入式码字与共享状态）

- 码字关系：同一编码状态机下 `code56 = code64 >> 1`、`code48 = code64 >> 2`
  是实现的结构性质。测试用三个持续运行的编码器实例贯穿整段（按完整采样对切块
  喂入），逐码字验证，不每个块重建实例。
- 状态锁定：用于自适应的四位低带索引（`ilow>>2`）在三种码率下相同，因此预测和
  尺度状态必须一致。测试逐码字比较三个解码器两路 band 里有意义的字段
  （`s/sp/sz/r/a/ap/p/d/b/bp/sg/nb/det`，逐字段比较，**不**对含 padding 的整个
  结构体做 memcmp），并验证三种输出音频确实不同（否则状态锁定是空证）。
- 手工码字：初始 `det` 已知（32/8），期望重建值按规范表手算
  （`floor(det*qm[...]/32768)`），逐码率验证重建表数值。低带细化位（六位低带
  索引的低两位）只进 qm6/qm5 重建路径、不进 qm4 自适应路径——用只差细化位的
  手工码字证明：重建值改变，后续预测历史不变。

### analysis 组（发送端 QMF）

- 参照是按自然时间顺序直接写出的 24 抽头卷积：延迟 `m` 偶数取 `c[m/2]`、奇数
  取 `c[(23-m)/2]`，高带的奇数延迟取负；int64 累加、显式向下取整（`>>14`），
  不照抄库里那个 24 格的搬移循环。
- 参照算出的 `xlow`/`xhigh` 分别喂给两个持续运行的 ITU test mode 编码器：低带
  历史在一路、高带历史在另一路，两个参照实例的声道历史不混用。从它们各取低 6
  位和高 2 位拼出期望码字，与真实编码器逐码字比对。
- 分别落在偶数和奇数采样位置的冲激提供手算锚点，固定两支滤波的相位、系数方向
  和缩放（含负数的向下取整）；低幅非对称双音和确定性正负序列覆盖连续段；信号
  末尾接静音，逐码字验证滤波尾音。16kHz 输入始终按完整采样对切块。
- 8kHz 模式另外验证：绕过 QMF 的低带输出与 ITU 参照一致，高带状态保持初始值
  不更新。

### synthesis 组（接收端 QMF）

- 参照 = 独立的 ITU test mode 解码器给出真实重建的子带 `rlow`/`rhigh`，测试按
  `u[2k]=rlow+rhigh`、`u[2k+1]=rlow-rhigh` 排成自然时间序列，再用自己的因果
  卷积（偶延迟抽头出一对中的第一个输出、奇延迟抽头出第二个，`>>11` 向下取整
  后限幅到 int16）算出期望 PCM，与真实解码器逐样本比对。
- 发送和接收分开验证；不做"有损往返后和原音相等"的判断。
- 参照卷积本身用手工 u 序列锚定：哪一路 u 驱动一对中的哪个输出、`>>11` 缩放、
  负数向下取整。

### packing 组（48/56 kbps 位流）

- 参照是测试自己按低位优先逐位组包/拆包的位计数模型，与库的实现相互独立。
  编码侧：逐块比对发出的字节，状态只比有效的残留位。解码侧：位计数决定每次
  调用交付的码字前缀和缓存里的有效位，交付的 PCM 前缀与非 packed 解码器交叉
  核对。
- 模型保留库既有的交付节奏：当前片段最后一个字节用完就立即返回，缓存里可能
  还有完整码字，要等下一次非空输入才继续，零长度调用不会把它排空。这是既有
  行为，不是丢样——测试按模型核对这个延迟，而不是把它修掉。
- 覆盖调用结束时的残留位与下一次补齐、1/3/11 字节的输入切分、完整码字刚好凑成
  整字节的序列（此时最后一个码字要靠一个填充字节冲出；填充位形成的多余码字不
  当成声音，只核对真实码字的 PCM 前缀和有效残留位），以及双实例交错不串历史。

## 退化检查 `tests/check_embedded_mutants.sh`

三份隔离副本各注入一处退化：

1. 发送端 QMF 把其中一支系数的方向反过来（由 analysis 组检出）；
2. 56kbps 解码误用六位的重建表（由 embedded 组的手工码字重建表检查检出）；
3. packed 编码在每次调用开头清掉残留位（由 packing 组检出）。

每份副本必须先编译成功，再跑同一组内容测试，并因数值差异失败（驱动退出码 4）
才算检出；构建错误、崩溃、缺文件都不算检出。另有一份未修改的对照副本必须全部
通过，用来排除测试环境本身的问题。
